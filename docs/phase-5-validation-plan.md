# Phase 5 MVP内部パイロット検証計画

## 文書情報

- 状態: 実施前
- 対象: Git編安定版MVP `STAGE-GIT-01`〜`05`
- 上位文書: [`requirements.md`](requirements.md)、[`game-design.md`](game-design.md)、[`../roadmap.md`](../roadmap.md)
- 関連文書: [`git-mvp-stages.md`](git-mvp-stages.md)、[`test-strategy.md`](test-strategy.md)

## 1. 目的

Phase 5では、現在の5ステージが機能することだけでなく、Git初心者であるユーザーが状態確認から問題解決を始め、操作の根拠を説明できる体験になっているかを内部パイロットで確認する。

この検証は、ユーザー1名による内部ドッグフーディングである。Codexと補助エージェントは進行、観察、分析、レビューを担当し、人間の検証参加者数には含めない。ユーザーは企画・実装内容を事前に知っているため、結果を未経験の一般ユーザーへそのまま一般化しない。

外部参加者が得られた場合の検証は将来課題とし、今回のPhase 5では、MVPの致命的な欠陥、学習上の誤誘導、操作上の大きな詰まり、ゲーム体験の弱点を発見して改善判断へつなげる。

## 2. 検証対象

- ステージ一覧、開始、再挑戦、進捗、最高スター
- `STAGE-GIT-01`〜`05`の導入、目標、守る条件、コマンド操作、出力、採点
- 4段階ヒントと案内量
- player resetとsystem recoveryの区別
- 自動クリア後の自己確認、技術振り返り、成長beat
- Runner待ち時間、エラー表示、workspaceとコンテナのcleanup
- Chapter 0を優先して追加すべき基礎知識上の詰まり

## 3. 今回検証しないこと

- 外部学習者に対する統計的な学習効果
- Chapter 0、Chapter 2、Git編Finaleの具体的なステージ設計
- Javaコードレビュー編、SQL編、Docker・CI/CD編
- 新しい機能、画面、DB、Runner、fixtureの実装
- macOS、Linux native、Windows on Armなど初期対応外の環境
- クラウド、外部公開、実在するremoteやGitHubとの連携
- 負荷試験、カバレッジ測定、全テストの再実行

## 4. 役割分担

### ユーザー

- 唯一の人間プレイヤーとして、Stage 1から5まで順にプレイする
- 操作前の仮説、分かりにくい言葉、迷い、待ち時間、不安を口に出す
- アプリ内ヒント以外の正解をCodexへ尋ねず、必要な場合は外部支援を受けた事実を記録する
- クリア後に、壊れていた状態、採用した操作が安全な理由、避けた方法を説明する
- 物語、テンポ、達成感、スターとresetへの率直な感想を伝える

### Codex

- 正解を先に教えず、実施手順と観察項目だけを案内する
- 時刻、ヒント、reset、詰まり、待ち時間、外部支援、説明内容を記録する
- システム障害とプレイヤーの判断上の失敗を分離する
- 終了後に合格基準へ照らして結果を整理し、改善候補を優先順位付きで提示する
- 変更が承認された場合だけ、通常のレビュー・実装・対象限定テスト工程へ進む

### 補助エージェント

- ライブプレイ中の正解提示には使用しない
- バムは、記録された物語、テンポ、没入感、成長beatの問題だけを必要に応じて評価する
- 井上は、承認された非軽微な技術変更の方針と差分だけを通常工程で評価する
- 中谷は、実装後にメインが未実行の対象限定テストだけを担当する

## 5. 実施前提

1. `main`がremoteの最新状態と一致し、作業ツリーがcleanである。
2. Windows 11 x86_64、Docker Desktop WSL 2 backend、Linux containerを使用する。
3. Java、PowerShell、Docker、Maven、PostgreSQLを含む既存のlocal起動前提を満たす。
4. 実施開始時にDocker Desktopを起動する。
5. 既存の進捗やDB volumeを、検証のために無断で削除しない。既知の進捗が初回体験へ影響する場合は、その影響を記録する。
6. 通知、別作業、Codexによる実装を止め、1回のプレイ区間では検証だけを行う。

## 6. 実施手順

### 6.1 起動確認

1. Codexがlocal環境のpreflightとアプリ起動を補助する。
2. ユーザーがステージ一覧を開き、表示、進捗、導線を確認する。
3. システムエラーがある場合はプレイ評価を止め、技術問題として分離して記録する。

### 6.2 各ステージのプレイ

Stage 1から5まで、各ステージで次を行う。

1. 導入と守る条件を読む。
2. 状態変更コマンドを打つ前に、「何が壊れていそうか」「最初に何を確認するか」を説明する。
3. アプリ内の機能とヒントだけで操作する。
4. 目立つ待ち、入力拒否、Gitエラー、画面上の迷いをその場で申告する。
5. クリア後、解説を開く前に復旧完了の根拠を説明する。
6. 解説を確認し、自分の理解との差を申告する。
7. 物語の長さ、緊張、達成感、次へ進みたいかを短く評価する。

player resetは少なくとも1ステージで実際に確認する。ただし、問題を解くためにresetが必要だと判断した場合は、評価を守るために我慢せず使用する。system recoveryはplayer resetとして扱わない。

### 6.3 転用確認

5ステージ終了後、Codexが元のfixture名やobject IDを使わない類似状況を4問提示する。ユーザーは実コマンドを実行せず、最初に確認する状態、採用する方針、守る対象を説明する。問題文と模範観点は実施時までユーザーへ開示しない。

### 6.4 振り返り

次をユーザーへ確認する。

- どのステージで目的または画面の見方を見失ったか
- 正解を知るより先に、自分で調べている感覚があったか
- resetを使うと3スターを失うため、安全な試行錯誤を避けた場面があったか
- 自動クリア後の自己確認だけで、復旧完了の根拠を考えられたか
- ライブworkspace上で確認操作や復旧報告をしたいと感じたか
- 物語が短すぎた、長すぎた、正解を教えすぎた場面があったか
- Chapter 0で先に学びたかったGitの基礎概念は何か

## 7. 記録項目

| 項目 | 記録内容 |
|---|---|
| Stage | `STAGE-GIT-01`〜`05` |
| 所要時間 | 開始からclearまで。システム障害時間は別記する |
| 最初の仮説 | 壊れていると思った状態 |
| 最初の確認 | 状態変更前に確認しようとしたこと |
| 最高hint level | 0〜4 |
| reset | player reset回数、理由、system recoveryとの区別 |
| 外部支援 | Codexなどアプリ外から正解情報を得たか |
| 主な詰まり | 用語、画面、Git出力、操作、待ち時間 |
| Clear・スター | clear可否と取得スター |
| 復旧根拠 | クリア後に説明できた内容 |
| 物語評価 | 長さ、没入感、緊張、達成感、正解誘導 |
| 改善候補 | その場で思いついた修正ではなく、観察した問題 |

実施後の結果は、別途作成する`phase-5-validation-results.md`へ記録する。この計画作成時点では結果文書を作成しない。

## 8. 合格基準

### 8.1 機能・安全性の必須条件

1. 5ステージすべてを開始し、期待状態へ到達してclearできる。
2. 少なくとも1ステージでplayer reset後に初期状態から再挑戦できる。
3. clear、reset、終了後に今回のattempt由来のchallenge containerが残らない。
4. ステージ一覧へclear状態と最高スターが反映される。
5. 入力拒否、Gitエラー、system recoveryが混同されず、進行不能な未処理エラーがない。
6. 正解の具体的なcommandまたは対象は、各ステージで定めたhint levelより前に表示されない。

### 8.2 学習体験

1. 5ステージ中4ステージ以上で、状態変更前に妥当な最初の確認方針を説明できる。
2. 5ステージ中4ステージ以上を、具体的解法を示すhint level 4なしでclearできる。
3. 5ステージ中4ステージ以上で、「壊れていた状態」「採用方法が安全な理由」「避けるべき近似解」のうち2項目以上を説明できる。
4. 終了後に、公開済み履歴へ使う`revert`と、未公開のlocal履歴を戻す`reset`の使い分けを説明できる。
5. 類似状況4問中3問以上で、妥当な確認方針、復旧方針、守る対象を説明できる。

### 8.3 操作・ゲーム体験

1. 5ステージ中4ステージ以上で、外部説明なしに目的と守る条件を説明できる。
2. 目的不明、画面の見方不明、文章量を理由とする進行中断がない。
3. 通常commandの90%以上が10秒以内、ステージ開始とresetが30秒以内に完了する。超過は環境要因とアプリ要因を分けて記録する。
4. 5秒を超える処理待ちで、処理中か停止したか判断できない場面を重大な操作上の問題として記録する。
5. player resetが必要だと思ったのに、3スターを守る目的だけで使用を避けた場面がない。
6. 5ステージ中4ステージ以上で、ライブworkspaceを保持しなくても自己確認から復旧根拠を説明できる。
7. 「長すぎて読み飛ばした」「正解を先に教えられた」と感じる導入が2ステージ以上にない。

### 8.4 Chapter 0の判断材料

次のいずれかが2ステージ以上の進行へ影響した場合、Chapter 0をPhase 5後の優先候補とする。

- working tree、index、HEADの違いが分からない
- `status`、`diff`、`add`、`commit`、branch切替の前提が不足している
- 何を確認してから状態変更すべきか判断できない

これは現在のChapter 1を不合格とする条件ではなく、初心者向け導線の優先順位を決める材料とする。

## 9. 問題の重大度

| 重大度 | 定義 |
|---|---|
| Critical | clear不能、正常な変更の喪失、cleanup不能、安全境界違反、誤ったGit判断を正解として教える問題 |
| Major | 目的や守る条件が理解できない、正解の先出し、安全な試行錯誤の阻害、自己確認が複数ステージで成立しない問題 |
| Minor | 意味を変えない文言、配置、演出、単発の軽い迷い |

## 10. 判定

- `PASS`: 機能・安全性の必須条件をすべて満たし、学習体験と操作・ゲーム体験の数値基準を満たし、未解決のCriticalまたはMajorがない。
- `CONDITIONAL`: Criticalはないが、学習・操作基準の未達またはMajorがあり、対象を限定した改善と再確認が必要である。
- `FAIL`: Criticalがある、または複数ステージを完走できず、現在のMVPを検証可能な状態として扱えない。

Phase 5完了には、検証結果を記録し、採用したCritical・Majorの修正と対象限定の再確認を終え、要件またはゲーム設計へ必要な判断を反映することを求める。MinorはPhase 6への阻害条件にせず、費用対効果で採否を決める。

## 11. 中断と再開

- Docker、Runner、DB、アプリの障害が発生した場合はプレイヤー評価を止め、技術障害として切り分ける。
- 障害対応中の時間、system recovery、Codexによる技術操作をプレイヤーの所要時間、reset、ヒント使用へ加算しない。
- 修復後は、影響を受けたステージだけを再実施する。共通画面、共通状態機械、採点共通部を変更した場合だけ、必要範囲を再評価する。
- 1回のプレイ中に改善実装を始めない。観察と解決策を分離する。

## 12. Phase 5終了時の成果物

- 内部パイロットの記録と判定
- Critical、Major、Minorに分類した問題一覧
- 採用・保留・不採用を分けた改善案
- resetと3スターの維持または変更判断
- 自己確認の維持、軽量化、または復旧報告再検討の判断
- Chapter 0を次の優先章とするかの判断材料
- Git編を継続改善しPhase 6へ進むかの判断
